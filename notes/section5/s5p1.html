1 What an agent is

An agent is a program in which a language model decides the next step.

  • The model gets a task and a list of functions it may call. The functions are the tools.
  • The model asks for a tool. Our code runs it and sends the result back.
  • Repeat until the model gives the answer. This is the loop.

1.1 The basic elements

  1. Model. The API call of Section 2.4.
  2. Tools. Ordinary functions. Each one has a one-sentence description for the model.
  3. Instructions. The system prompt: what to do, in which order.
  4. Loop. Ask, run the tool, show the result, repeat, stop.

The receipt is the list of all tool calls, with arguments and results. We keep it to check the answer.

1.2 One call, a workflow, or an agent

A model call is one request to the language model: we send text, it sends text back. chat$chat("...") in Section 2.4 is one model call. There are three ways to use a model for a task. Take the task of this page: build the R package of Tech Guide 3.

  • One model call. “Write an R package named pvals with these three functions.” The model writes code as text. Nothing is saved, built, or checked.
  • A workflow. A fixed recipe written by us. Step 1: ask the model for the code. Step 2: our script saves the files and runs R CMD check. Step 3: ask the model to fix the errors. The model never chooses the next step. We do.
  • An agent. We give the model the tools (write a file, run R code) and the task. The model chooses the steps: write DESCRIPTION, write the R file, run roxygenise, build, check, fix, check again. We did not decide the order. It did.

Use the simplest one that works. Build an agent only when the steps are not known in advance.

2 Build an agent

On this page we write the specification of an agent, and a coding agent writes the script from it: Claude Code on the instructor’s laptop, Copilot in the Codespace. The one-tool agent below is the only script we read by hand.

2.1 The smallest agent

Run in Codespace: a real model needs a key. Set OPENAI_API_KEY once in ~/.Renviron, or as a Codespaces secret.

One tool and one task. ellmer runs the loop inside chat$chat().

library(ellmer)

# 1. a tool: an ordinary R function
run_r <- function(code) paste(capture.output(print(eval(parse(text = code)))), collapse = "\n")

# 2. its description: what the model reads instead of the code
tool_run <- tool(run_r, "Run one piece of R code and return what it prints.",
                 arguments = list(code = type_string("The R code to run.")))

# 3. the model, with instructions, and the tool attached
chat <- chat_openai(system_prompt = "Use the tool to compute. Never guess a number.")
chat$register_tools(list(tool_run))

# 4. print the receipt as it happens
chat$on_tool_request(function(request) cat("-> run_r:", request@arguments$code, "\n"))
chat$on_tool_result(function(result)   cat("<-", result@value, "\n"))

# 5. one task. ellmer runs the loop: ask, act, observe, repeat, until the model answers.
chat$chat("What is the 0.975 quantile of the t distribution with 10 degrees of freedom?")

The five comments are the four elements of Section 1.1. Comments 1 and 2 are the tool, comment 3 is the model and the instructions, and comments 4 and 5 are the loop, which ellmer runs for us, and the receipt it prints.

2.2 The specification

A specification is a short text that says what the agent must do. It has four parts: the task, the tools, the instructions, and the repo layout. Here it is for an agent that writes an R package, the package of Tech Guide 3:

Task
  An R package named pvals that computes two-sided p-values from a test statistic:
  pval_z(z) for a standard normal statistic, pval_t(t, df) for a t statistic,
  and pval_chisq(x, df) for a chi-square statistic (upper tail).

Tools
  write_file(path, content): write a text file inside the sandbox; create folders as needed.
  read_file(path): read a text file inside the sandbox and return its content.
  list_files(): list every file in the sandbox, one per line.
  run_r(code): run R code in a fresh R session inside the sandbox and return what it printed.
    High risk: it runs any R code.

Instructions (the system prompt)
  You are an experienced R package developer. Build the package inside the sandbox,
  using only the tools, in this order.
  1. Write pvals/DESCRIPTION and pvals/R/pvals.R with roxygen comments.
  2. Run roxygen2::roxygenise('pvals') to create NAMESPACE and man/.
  3. Run R CMD build, then R CMD check --no-manual on the .tar.gz file.
  4. Read the check output. Fix every ERROR and WARNING, then check again,
     until the check ends with Status: OK.
  5. Try each function once with run_r. Do not install the package.
  6. Report the files you wrote, the final check status, and the path of the .tar.gz file.
  Never guess what a command printed; read the tool result.
  Do not write files outside the package folder.

Repo layout
  README.md    what the agent does, which key it needs, how to run it
  agent.R      the tools, their descriptions, the instructions, and chat$chat()
  sandbox/     the folder the agent works in; the package it builds goes here
  receipts/    one saved .rds file per run

Copy the block and change the four parts for your own task. Note that each tool is one line: its name, its arguments, and one sentence. If you cannot write that line, the model cannot use the tool.

2.3 The prompt for the coding agent

Paste the specification, then this prompt, into Claude Code or Copilot:

Build this repository from the specification above, in R with the ellmer package.
- The tools are plain R functions. Each one gets a tool() description that says
  what it does and what each argument means.
- write_file and read_file must refuse any path outside sandbox/.
- Print every tool request and every tool result as it happens

- After the run, save chat$get_turns() and chat$get_tokens() to receipts/ with saveRDS.
- Read OPENAI_API_KEY from the environment. Never write a key into any file.
- Show me agent.R before you run it.

Read the script it shows you, then run it and keep the printed receipt. Our own version is run/s5p1_pkg_agent.R; on Nov 4, with gpt-5.4, it took five tool calls and the check ended with Status: OK.

2.4 The receipt checklist

The receipt is the printed list of tool requests and results. Read it before you accept the package:

  • Is there an R CMD check call in the receipt? If the model reports Status: OK without one, the report is a guess. If there is one, does the report match its output?
  • When a check failed, what did it change before the next check?
  • Did it write a file outside the package folder pvals/? The instructions forbid this, but write_file only refuses paths outside the sandbox, so such a file passes the tool.
  • Did every number and name in its report come from a tool result you can see? In our run the model invented an author name and a RoxygenNote version. Both came from memory, not from a tool.

A loop needs an exit, and a person needs a way to step in:

  • There are four exits: a final answer, a maximum number of steps, an error the loop cannot recover from, and a structured final output, where the model returns an object of a declared type (structured output).
  • run_r is the high-risk tool: it runs any R code, anywhere on the machine. Set ASK <- TRUE at the top of the script to approve each run_r call yourself. This is human intervention.
  • Hand control back to a person after several failures, or before a high-risk action such as deleting a file.

2.5 Frameworks

In practice you do not write the loop. A framework, a package that runs the loop for you, does it.

  • ellmer (R): tool() describes, chat$register_tools() attaches, chat$chat() loops. The receipt is chat$get_turns().
  • OpenAI Agents SDK and Claude Agent SDK (Python): the same loop as a library. The Claude Agent SDK is the loop of Claude Code, with built-in tools to read and edit files, run commands, and search the web.
  • MCP (Model Context Protocol): a standard format for describing a tool. Write the tool once in this format, and any model that supports MCP can call it.

In a new framework, find the four elements and the exit conditions.

3.2 An agent’s success rate

  • Run a real agent on the same task twice and you can get two different receipts. The model draws its output at random (sampling controls), so which tool it calls, and with what arguments, is random too.
  • So whether it succeeds is random. We estimate its probability of success, give it a confidence interval (Section 3.2), and choose the number of runs (Section 3.3).

Here is a stand-in model that makes the same kinds of mistakes a real model makes. Sometimes it answers without bootstrapping. Sometimes it bootstraps the median when the task asked for the mean. Sometimes it misspells the statistic, gets an error, and recovers.

3.4 Audit the agent

Three receipts from the bootstrap agent. The task was the same each time: the mean failure time and its bootstrap standard error. Each receipt has a problem. None of them threw an error.

By hand: read each receipt and write one sentence saying what went wrong and which course principle it violates. Done when you can name all three without running anything. No AI for this block.

  • R
  • Python
NoteSolution

Receipt 1: the wrong statistic. The task asked for the mean; the tool was called with stat = "median". The number 28.78 is the standard error of the median. Every step succeeded, and the answer is wrong. Principle: read the arguments, not just the results.

Receipt 2: the number was never bootstrapped. There is no boot_se call. The model computed \(s/\sqrt{n}\) from memory, the standard error formula of Section 3.2, and called it a bootstrap standard error. It is close to the bootstrap value, which makes the error hard to see. Principle: every number must come from a tool call. A number with no tool call behind it is a guess.

Receipt 3: false confirmation. The two boot_se calls use the same seed, so they are the same computation twice. Two identical numbers are not two independent bootstrap runs. Principle: replication means a different sample or method; here, a different seed. The answer is correct, but the claim of confirmation is not.

Two of the three receipts give a reasonable number. An audit checks how the answer was computed, not only the answer.
